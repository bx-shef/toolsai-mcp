# Живое наблюдение на тестовом портале

> Last reviewed: 2026-10-17

Зачем: тесты гоняют сервер против подставного портала и проверяют то, что мы о портале
**думаем**. `npm run smoke` показывает, что сервер делает с **настоящим** порталом и что
видит модель.

## Как устроено

Запуск: `npm run build && npm run smoke`.

`smoke/observe.mjs` запускает собранный сервер (`.output`) и «портал-посредник»:

- OAuth посредника подставной — выдаёт токены, вход проходит как у claude.ai (регистрация,
  согласие, возврат с портала, обмен кода с PKCE);
- `/rest/*` посредник пересылает на **тестовый** облачный портал через входящий вебхук.
  Метод и параметры сервера уходят как есть, без подмены;
- перед прогоном засевает компанию, контакт, лид, сделку, задачу и дело с меткой
  `mcp-smoke-<время>`, после прогона удаляет их;
- зовёт `initialize`, `tools/list` и каждый инструмент, плюс крайние случаи: ID строкой,
  несуществующая запись, неверный аргумент, истёкший access (посредник отвечает
  `expired_token` — сервер обязан обновить вход и повторить);
- протокол — `smoke/out/<метка>.md` (в git не попадает): что ушло на портал, за сколько, что
  получила модель, строки журнала.

Вебхук — только в `.env.b24test` (в `.gitignore`): `B24TEST_WEBHOOK=https://b24-….bitrix24.by/rest/1/…/`.
Скрипт откажется работать с адресом, не похожим на облачный тестовый портал. На боевой портал
посредник не ходит.

Чего не проверяет: настоящий OAuth портала (вход по `/oauth/authorize/` и права сотрудника,
отличного от владельца вебхука) — это `docs/OAUTH_CHECK.md` на коробке.

## Что увидели 2026-10-13

- Все 9 инструментов отвечают; на портал — ровно один REST-вызов на инструмент, 200–240 мс.
- Истёкший access: `401 expired_token` → refresh → повтор, модель ошибки не видит.
- **Найдено и исправлено:** `crm.deal.get` без записи отвечает `{"error":"","error_description":"Not found"}`,
  SDK теряет описание и даёт `ERR_BAD_REQUEST` — модель получала «Битрикс24 отказал». Теперь — «Не найдено».
- **Найдено и исправлено:** `tasks.task.get` без задачи отвечает `{"result":[]}` без ошибки —
  модель получала пустой массив. Теперь — «Не найдено».
- **Найдено и исправлено:** списки отдают ID строками (`"id":"6"`), а `*_get` требовали число —
  модель, передав ID из ответа как есть, получала ошибку проверки. Теперь строка принимается.
- Карточка сделки — ~1,3 тыс. символов, больше половины полей пустые (`null`). Кандидат на
  сокращение (выбрасывать пустые поля) — в план, не сделано.
- На тестовом портале лид при создании сразу конвертируется в сделку (режим «без лидов»), и
  поиск по названию находит «сделку-лид». Свойство портала, не ошибка.

## Инструменты решений Вайбкода (#21–#29)

С 2026-10-17 прогон проверяет и инструменты задач #21–#29: поиск по телефону и почте, подзадачи,
сообщения, рабочее время, диск, каталог, документы по шаблону, статистику звонков. Для этого он
засевает товар каталога и телефон с почтой у контакта. Всё созданное убирает за собой: документ,
папку, подзадачу и товар. В конце протокола раздел «Итог» — ✓ или ✗ на каждый вызов; ✗ стоит
только у нарочно неверных вызовов. Сообщение `im_message_send` уходит пользователю 1 и не
удаляется. Рабочий день не трогаем: смотрим только `worktime_status`.
