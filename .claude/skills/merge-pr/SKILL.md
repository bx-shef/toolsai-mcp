# Мерж PR

> Last reviewed: 2026-10-13

Источник правил — `docs/AGENT_RULES.md` §4. Этот навык — порядок действий.

⚠ Мерж в `main` = выкат на VM портала за ~5 минут (`docs/DEPLOY_BITRIXVM.md`).

## 1. Перед мержем — всё должно выполняться

1. **Свежий `main`**: `git fetch origin main`, влить в ветку, `npm run typecheck && npm run build && npm test`, пуш.
2. **CI зелёный** на последнем коммите (`ci`, `docker-build`).
3. **Живой портал**: PR меняет вход, инструменты или зависимости — в описании PR сказано, проверено
   ли на портале (каким сотрудником, что видно). Не проверяли — так и написать.
4. **Треды ревью закрыты** — на каждый ответ или правка.
5. **Follow-up issues — по-русски**, с контекстом: что, почему, `файл:строка`, как проверить, ссылка на PR.
6. **Squash-сообщение** (`AGENT_RULES.md` §4.2): `тип(область): решение` по-русски, тело — довод и
   цена; ломающее — `тип!:` и `BREAKING CHANGE: <что сделать на сервере, в nginx или на портале>`.
7. **Штампы `> Last reviewed:`** в затронутых документах и навыках — на дату мержа.

Что-то не выполняется — не мержить; сказать, что именно.

## 2. Мерж

Squash-мерж. Сообщение — из п. 6.

## 3. После мержа

1. **Выкат**: CI → Build & Push to GHCR зелёный. Есть доступ к серверу — через 5–10 минут
   `curl -s 127.0.0.1:3100/health` показывает новый `commit`; нет доступа — сказать владельцу, что
   проверить (`tail /home/bitrix/mcp/deploy.log`).
2. **Удалить ветку** (удалённую и локальную).
3. **Issue закрыт этим PR — комментарий по-русски**: бодрый, в меру шутливый; пара ссылок на
   документацию (открыть до публикации); спасибо от владельца. Закрыть issue.
4. **Оценка проекта** простыми словами: сделано / следующий шаг / что мешает — и то же в
   `docs/project-map.md`.
